## Evidence gathered from current code

### MultiAgentV2 guarantees now present

- `spawn_agent` requires an explicit stable `task_name`; canonical paths are returned.
- Spawned agents can spawn descendants.
- `send_message` queues inter-agent communication without triggering a new turn.
- `followup_task` triggers an idle target and queues to a running target for delivery at message boundaries or after a pending tool call.
- `wait_agent` waits on mailbox activity but deliberately returns no message contents.
- `list_agents` returns only canonical agent names and last known coarse statuses.
- A detached completion watcher and terminal-turn forwarding automatically send a child's final status/final message to its direct parent.
- InputQueue stores queued inter-agent mail in session memory and wakes mailbox subscribers; queue-only mail may be deferred to the next parent turn.

### Guarantees not found

- No automatic periodic child progress reports or heartbeat generation.
- No automatically maintained compact mission board or parent-readable progress snapshot.
- No automatic role transition from `default` to `concertmaster`/`conductor`.
- No harness mechanism that forces a role to delegate rather than work locally.
- No automatic time-budget ownership/intervention loop.
- No proactive permission-scope prediction before a requested action.

### Important tension in current tool guidance

- Current spawn tool guidance tells the model not to spawn unless explicitly authorized and to keep urgent/critical-path/tightly coupled work local.
- It recommends delegating bounded independent sidecars and doing useful local work while they run.

### Guardian / permissions finding so far

- `request_permissions` normalizes and submits a requested additional permission profile to the environment/client.
- Guardian/auto-review routes approval requests through a reviewer after a tool/action requests approval.
- No code examined so far predicts future git write scopes or front-loads permission requests.
- Therefore Guardian currently appears to improve safety/approval routing, not replace early permission planning. More code/docs/tests still need inspection before final classification.

### Release and source baselines

- The local Codex checkout is `main` at `bb5054fe47abe73ecbbd454751066a28c89f4bb9` (2026-08-03), so it contains a small amount of post-0.146 work. The running desktop harness exposes the same current MultiAgentV2 and permission surfaces inspected locally.
- The 0.146 released loader recursively discovers `.toml` files in each config layer's `agents/` directory. A standalone discovered role must resolve a nonblank `name`, `description`, and `developer_instructions`; `nickname_candidates` is role metadata; remaining top-level keys form an ordinary high-precedence Codex config layer. The repeated `[agents.<role>] config_file = ...` registrations are therefore redundant compatibility declarations, not required structure.

### Model and delegation semantics

- Official GPT-5.6 guidance confirms `gpt-5.6` aliases `gpt-5.6-sol`; Sol is the frontier tier, Terra balances capability and cost, and Luna is the efficient/high-volume tier. The API advertises reasoning through `max`; `ultra` is a Codex harness mode rather than an API reasoning value.
- In current Codex, selecting `ultra` sends backend reasoning effort `max` and injects a developer message enabling proactive delegation. Non-Ultra work defaults to an explicit-request-only delegation developer message unless `features.multi_agent_v2.multi_agent_mode_hint_text` supplies a custom policy.
- This is a real replacement for prompt text whose only purpose was to authorize a conductor/concertmaster to delegate. It is not an automatic role selector or phase-transition mechanism.
- `DEFAULT_ROLE_NAME` is still literally `default` when `agent_type` is omitted. Role application explicitly says it does not decide when to spawn or which role to use. No code path was found that converts a planning-to-execution transition into `concertmaster` or `conductor`.
- MultiAgentV2 full-history forks reject an `agent_type` override and inherit the parent role/instructions. To create a different role, the caller must use `fork_turns = "none"` or a positive last-N value. This needs to inform any default-to-orchestrator handoff language.

### MultiAgentV2 communication and state

- `spawn_agent` requires a stable `task_name` and produces canonical hierarchical task paths. This supersedes old spawn-handle recovery boilerplate.
- `send_message` queues mail without triggering a turn; `followup_task` triggers an idle non-root target and is delivered at a running target's message/tool boundary; `wait_agent` wakes on mailbox or steered user activity but intentionally returns no message contents.
- Terminal V2 child turns automatically enqueue a standard `FINAL_ANSWER` envelope to the direct parent only. There is no automatic grandchild-to-root fan-in; the intermediate orchestrator must remain alive and synthesize upward.
- The completion send is queue-only and fails silently (debug log) when the direct parent is dead/unloaded. A current test explicitly verifies that a dead direct parent receives nothing and the root is not notified. Thus "automatic final delivery" is a live-parent convenience, not a durable hierarchy-wide guarantee.
- `InputQueue` stores pending mailbox messages in an in-memory `VecDeque`. `list_agents` lists only currently live/loaded agents and their coarse status. Neither is a durable mission board, progress ledger, or recovery snapshot.
- No periodic progress generation, heartbeat, deadline, ownership check, or time-budget intervention exists in the harness. These remain workflow responsibilities, although their old exact implementation can be simplified.

### Time awareness

- Current-time reminders are a real 5.6-era improvement. This configuration enables them every 60 seconds for any inference and exposes the interruptible clock tools.
- The reminder only injects the current UTC time. It does not create deadlines, measure lane progress, send heartbeats, or intervene. Role prompts can rely on the injected clock instead of repeatedly calling a time tool, but must still define any deadline/heartbeat policy that matters.

### Guardian and permission behavior

- `request_permissions` parses and normalizes the exact permission profile supplied by the agent, then calls the session permission flow. Guardian routing begins only at that approval request (or another concrete action requiring review).
- Guardian assesses the exact requested action against the retained transcript and policy. It can perform read-only local checks, but runs with `approval_policy = never`, a read-only permission profile, no inherited developer instructions, and Apps, Plugins, Web Search, MCP servers, and multi-agent features disabled.
- Guardian therefore improves risk/authorization review and can approve safe requested scopes automatically. It neither predicts future filesystem/git paths nor proactively asks for permissions the working agent has not identified.
- Current permission developer text explains scoped `with_additional_permissions`, direct `request_permissions`, and full escalation, but contains no requirement to inventory likely write scopes before expensive work.
- Conclusion: Guardian does not supersede early permission planning for unattended work. The old control should be narrowed to exact, evidence-backed preflight (repository root, resolved git/common dirs, planned worktrees, known external paths), not restored as a broad blanket request.

- Official mapping is **Sol ≈ prior unsuffixed/full model**, **Terra ≈ prior mini**, and **Luna ≈ prior nano**.

## Minimum coherent 5.6-era instruction contract

### 1. Spawn and mission contract

Every delegated task must be self-contained enough to survive context loss and should name, in proportion to the work:

- objective and concrete deliverable;
- scope, non-goals, and owned/write surface;
- dependencies and success evidence;
- delegated authority, including whether nested delegation or external side effects are allowed;
- requested reporting boundaries and any manager-owned `next_check_by` when delay matters;
- durable checkpoint path and owner when the mission is unattended, long-running, or context-risky.

When a spawn changes roles, use `fork_turns="none"` or a positive last-N value and carry this contract explicitly; a full-history fork cannot change `agent_type`.

### 2. Default transition guard

`default` remains a direct-working generalist unless the user or its parent has explicitly authorized multi-agent work. Once such authorization exists, the root/default agent becomes the conductor-of-record at the current root: it creates the compact board, selects roles, supervises, and synthesizes. It must not spawn a conductor merely to change labels or silently fall back into bulk local execution. ### 3. Manager control plane

- `conductor` owns the whole mission, `concertmaster` a major workstream, and `principal` a narrow squad. All three are Ultra and may delegate proactively within their explicit charter.
- Use only current V2 controls: stable `task_name`, `spawn_agent`, `send_message`, `followup_task`, `list_agents`, `wait_agent`, and `interrupt_agent`.
- Canonical task paths are **live control handles**, not durable records. Direct messages and completion envelopes are also transient. Canonical per-thread rollouts plus the persisted spawn graph are the exhaustive audit evidence; they can be viewed as one logical owner-attributed stream without asking agents to duplicate every action.
- Maintain a compact live board with owner, surface, state, latest evidence, next action, dependency, and next manager-owned check. Ask children for updates at material boundaries, blockers, and completion. When a deadline matters, the manager must arm an actual bounded `wait_agent` call or watcher and check on wake/timeout; a requested child deadline is not a timer.
- Keep every intermediate manager alive until its descendants are terminal and their results have been synthesized upward. Do not assume grandchild results reach root automatically.
- For long/unattended/context-risky missions, name one durable checkpoint file and one writer, normally `archivist`. Use it for curated decisions/current state rather than a duplicate event ledger, and refresh it at phase boundaries and before a context rollover. Valkey may support finite-TTL locks/dedup/handoff state only; it is never the recovery source of truth.
- Preflight likely permission-critical paths early through `steward` when unattended work, git metadata, worktrees, or external paths are expected. Request only missing, exact scopes.
- External notifications, recurring cadences, account actions, and other real-world side effects require authority inherited from an explicit user request; delegating to a specialist does not create that authority.
- At completion, verify success criteria, close or interrupt unneeded descendants, and synthesize evidence and residual risk rather than forwarding raw child output.

### 4. Durable state and communications roles

- `archivist` is the single writer/reconciler for an assigned durable checkpoint and must mark stale or disputed facts rather than silently normalizing them.
- `publicist` owns user-facing communication strategy only when assigned; `scribe` drafts polished synthesis; `herald` emits short alerts only through an explicitly authorized channel and event class.
- These roles report to the parent; they do not create their own swarms, cadence, notification authority, or competing state schema.
- Direct messages are live coordination. Canonical rollouts and lineage are exhaustive audit evidence; durable semantic state belongs in the normal thread, destination system, or named checkpoint file. Exact per-role Valkey schemas should be removed from standing prompts.

### 5. Leaf-role lifecycle

- Own a bounded surface, preserve unrelated work, and finish the assigned deliverable.
- Investigate discoverable facts and make safe progress, but do not self-recast, invent authority, or spawn descendants unless the task explicitly authorizes delegation.
- If a different specialist is needed, report the recommended handoff to the parent instead of attempting an unauthorized transition.
- Honor the parent's reporting contract with concise, evidence-bearing status at meaningful boundaries, blockers, and completion. A manager owns any deadline check. Final delivery to a live direct parent is automatic; return cleanly instead of continuing into adjacent work.
- Use transient coordination state only when the parent supplies a namespace/schema and direct messaging is insufficient; never invent a new shared-state convention.

### 6. Role-specific retained controls

- `analyst`: investigate what is discoverable; enumerate unresolved interpretations; never silently choose when scope, authority, success criteria, or side effects differ; state harmless assumptions explicitly.
- `steward`: resolve repo/git/common/worktree paths early, compare them with current permissions, and request only missing exact scopes before git writes become critical.
- Read-heavy analyst/explorer/researcher/reviewer/watcher retain `sandbox_mode="read-only"` and require explicit task-level authorization before any exceptional edit workflow.

### Canonical rollout and lineage persistence

- `rollout/src/recorder.rs` explicitly calls rollout JSONL the canonical session record. Files are opened in append mode; every serialized line receives a UTC timestamp, is written with a newline, and is flushed. Pending writes are retried across reopen/recovery on failure.
- This thread's actual rollout contains developer/user/assistant messages, reasoning summaries, tool calls and outputs, task lifecycle, compaction, world-state/turn-context snapshots, token events, and other response/event items. Child rollouts additionally persist inter-agent communication items.
- `state_5.sqlite` contains `threads` metadata with `rollout_path`, `agent_path`, `agent_role`, and `agent_nickname`, plus `thread_spawn_edges(parent_thread_id, child_thread_id, status)`. `AgentControl` restores V2 identities from this persisted graph even without reopening runtimes.
- Therefore the exhaustive durable source is the set of append-only per-thread rollouts plus the spawn graph. At the architectural level, those sources are sufficient to reconstruct one deterministic owner-attributed logical event stream live or retroactively, including archived `.jsonl.zst` rollouts. This audit does not design or implement a tailing/projection tool.
- Curated checkpoint/decision records still matter: exhaustive transcripts show what happened but do not replace an explicit current-state/accepted-decision summary. Treat the checkpoint as semantic state and the reconstructed logical stream as the audit view.

### Reporting deadline correction

- Nothing in a child contract or current-time reminder wakes a child at `next_update_by` or forces it to send a message.
- `wait_agent` does have an enforced timeout and returns a timeout snapshot; a dedicated watcher can own a long wait. Therefore a meaningful reporting deadline must be an action owned by the manager: arm a bounded `wait_agent` or watcher until the deadline, then refresh status and follow up/intervene. Child messages are useful evidence when they arrive, not the timer mechanism.
- Prompt wording must distinguish the behavioral request (report at material boundaries) from the runtime-enforced supervision action (manager waits/checks at the deadline). This is the evidence-supported reason the revised contract should behave better than the historical child-only deadline wording.

## Continuity architecture evaluation — provisional, not approved

- The operating contract v2.1.12 was read completely as an architectural artifact explicitly placed in scope; it was not activated wholesale as governing response behavior. Module E defines namespaced workstreams, a revisioned state envelope, one active writer, compare-before-write conflict handling, per-workstream isolation, fork/handoff semantics, and adapter-specific durability/reach.
- The companion control-design spec has already approved `~/.codex/.workstreams/<thread-id>/WORKSTREAM-STATE.md` as the first recovery lookup and rejected a prompt-only compaction fix. It treats direct runtime injection as the stronger later target and says the workstream record carries durable decisions/material blockers rather than a high-volume event log.
- Current MultiAgentV2 mail is session-scoped, in-memory, and stored in an apparently unbounded `VecDeque`; it is suitable for small low-latency control signals, not state payloads, backpressure, or recovery. V2 exposes canonical task names to the model but may hide underlying thread IDs, so child state paths must be supplied or injected rather than guessed.
- `WORKSTREAM-STATE.md` is a strong semantic checkpoint but does not wake work, efficiently carry high-frequency liveness, or by itself enforce atomic compare-and-swap. Existing workstream files already vary in Markdown structure, so deterministic machine recovery needs a canonical machine-readable envelope or a dedicated state helper/runtime resolver.
- Valkey is operationally persistent relative to agent threads and the Codex app, even though it remains non-authoritative and finite-lived relative to a workstream. It is suitable for latest-status projections, handoff/result snapshots, leases, bounded pending queues, deadlines, and deduplication. Mail should carry only a small pointer/revision signal; managers can recover latest state from deterministic Valkey keys when mail is lost.
- The local Valkey instance is a separate Homebrew service with RDB snapshotting, AOF disabled, no memory cap, and no eviction. It survives ordinary thread/app loss but can lose low-volume writes since the last snapshot after a Valkey/host crash, and unbounded or large payloads can consume host memory. It cannot be the only copy of authority, a pending external side effect, or state promised to survive host failure.
- Provisional layering: canonical rollouts/spawn graph = exhaustive evidence; per-workstream record = material semantic state; Valkey = bounded operational projection; mailbox = low-latency signal/control; runtime hook/extension = deterministic path resolution, checkpoint/rehydration, CAS/fencing; external supervisor plus durable outbox = execution or notification while Codex is down.
- Provisional swarm topology: one root mission workstream; child workstreams only for long-lived/context-risky manager lanes; short-lived leaves publish bounded status/result projections and rely on their canonical rollout rather than each owning a file. The mission workstream indexes child workstreams rather than accepting concurrent writes from every agent.
- Open design hinge: `writer_binding` currently conflates semantic control authority with the process/thread performing persistence. A robust swarm may need separate `control_owner`, `persistence_writer`, `recovery_owner`, and fenced `epoch` fields. A runtime state service is the strongest writer; a dedicated archivist is a plausible prompt-level interim writer but becomes a recoverable availability dependency.
